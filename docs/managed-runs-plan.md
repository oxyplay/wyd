Команды:

```text
wyd run --timeout 120s -- npm test
wyd run --memory 512 --enforce monitored --queue-timeout 60s -- npm test
wyd runs [--json]        wyd logs <id> [--follow] [--stream stderr]
wyd cancel <id>          wyd mcp --allow-run
wyd capacity [--json] [--set key=value ...]
```

Чтения (`runs`, `logs`, MCP `list_runs`/`get_run`/`read_run_output`) идут
из стора и файлов логов и работают без демона. `capacity` — исключение:
`wyd capacity` и web-провайдер без демона отдают настроенные лимиты с нулевой
загрузкой, а MCP `get_capacity` поднимает supervisor по требованию. Запуск и
отмена требуют supervisor: он стартует по требованию (flock + handshake) и
выходит после 5 минут простоя. SIGTERM/SIGINT сначала останавливает активные
запуски (grace 10 с), затем снимает сокет и выходит.

## Результаты platform spike (§1.3)

- Группа создаётся до exec (`process_group(0)`); лидер и потомки
  идентифицируются по `boot_id + pid + start_time`.
- Группа сигналится только пока живой член совпадает с записанной
  идентичностью — переиспользованный `pgid` не убивается; иначе `cleanup`
  `unknown`/`incomplete`.
- Родитель вышел, worker остался — покрыто тестом: групповой kill добивает
  worker, `cleanup=complete`.
- `setsid`/double fork/внешний daemon выходят из группы. Это известный
  непокрытый escape: тест проверяет границу (чужую группу не трогаем), а не
  мнимое покрытие.
- Потомок может удержать pipe после смерти запуска: дренаж продолжается, но
  запись прекращается по флагу завершения, и финиш запуска не ждёт
  посторонний pipe бесконечно.
- Deadline монотонный; wall-clock используется только как подстраховка от
  сна машины (остановка возможна раньше, никогда позже) и для истории.

## Результаты cgroup v2 spike (§2.3)

Проверено в контейнере (`scripts/linux-cgroup-e2e.sh`):

- контроллеры включаются **по уровням** (делегированный каталог →
  `wyd.slice` → `run-N`): `+memory +pids +cpu` в
  `cgroup.subtree_control` каждого каталога, начиная с делегированного; в
  cgroup с процессами включить их нельзя («no internal processes»), и мы
  никогда не переносим чужие процессы, чтобы это обойти;
- `memory.max`, `memory.swap.max` (0 при hard-лимите), `cpu.max`,
  `pids.max` применяются и читаются обратно — `effective` показывает
  принятые значения, а не запрошенные;
- ребёнок входит в cgroup в `pre_exec` (fork → attach → exec), поэтому
  `setsid`-потомок остаётся внутри: `cgroup.kill` его достаёт, а
  `cleanup=complete` подтверждается пустотой cgroup;
- OOM приписывается только по `memory.events` (`oom_kill>0`), не по факту
  SIGKILL;
- без делегирования discovery возвращает причину, capability =
  `Unavailable`, hard-запрос отклоняется до spawn.

## Что осталось

- **Linux проверен в контейнере** (`rust:1-slim-bookworm`, 2026-09-09):
  тесты зелёные, `clippy -D warnings` и `fmt --check` чисто, плюс сквозные
  прогоны `scripts/linux-cgroup-e2e.sh` (cgroup-бэкенд) и
  `scripts/systemd-delegation-e2e.sh` (делегирование от настоящего systemd,
  системный и user-менеджер). Это контейнер, а не desktop-Linux.
- **Sleep/resume** проверяется только логикой подстраховки, без реального
  теста сна. Что делать — задача B ниже.
- **macOS hard limits недоступны by design.** Память — `Monitored`
  (сумма RSS по process group, сэмпл каждые 200 ms), hard-запрос
  отклоняется до spawn. CPU/processes — advisory, бэкенда нет.
  Что делать — задача A ниже.
- **Измерения** — только один прогон на одной машине, debug-сборка (§2.7);
  как обещание скорости их публиковать нельзя.
- **Filesystem/network isolation и одноразовые среды** — отдельный
  дальнейший этап, в 1–2 не входят.

## Что делать дальше

Три задачи. Две из них осознанно привязаны к этапу изоляции (§3): и
macOS-лимитам, и реальному сну нужна VM, которую wyd умеет поднимать.

### A. macOS hard-лимиты — только вместе с backend'ом исполнения

Сейчас на macOS `monitored` + отказ на `--enforce hard`. Жёсткий лимит
средствами ядра там невозможен: cgroup v2 нет, `setrlimit` — на один
процесс (у каждого потомка свой лимит, агрегата нет), jetsam — глобальный
killer по давлению памяти, `launchd` — per-job. Подробнее в §2.4.

План в два уровня, оба исполняют запуски в Linux внутри macOS:

1. **Общий backend (дешевле).** Один Linux-инстанс на пользователя (Lima,
   Apple Virtualization, `containerization`); запуски идут внутрь него, а
   лимиты — per-run cgroup v2 внутри. Boot на каждый тест не нужен.
   Нужно: lifecycle инстанса, проброс cwd/env, стриминг вывода и exit-кода,
   идентичность запуска, честная деградация при недоступном backend.
   Приёмка: `aggregate_memory_limit`/`cpu_quota`/`process_limit` =
   `Available` при живом backend; `--enforce hard` реально приводит к OOM;
   backend недоступен → снова `Unavailable`, **никогда** не `monitored`.
2. **Одноразовая среда (§3).** То же плюс файловая/сетевая изоляция, кеш
   зависимостей, network policy.

Чего не делать: `setrlimit` как «жёсткий лимит», более частый polling,
автоматические изменения глобальной конфигурации ОС.

### B. Реальный sleep/resume — на suspendable VM

Логика уже есть и покрыта тестом: дедлайн запуска — `max(монотонное, wall)`,
очередь — на логическом времени (задача C). Не проверено поведение при
настоящем сне машины.

Где проверять: VM, которую можно усыпить и разбудить (`virsh suspend`,
qemu `system_wakeup`, Apple Virtualization). Приёмка:

- запуск с таймаутом T, сон дольше T, пробуждение → запуск останавливается
  в течение нескольких секунд, `outcome=timed_out`, `cleanup=complete`,
  `duration_ms` отражает реальное (wall-clock) время;
- запрос в очереди переживает сон и истекает по `queue_timeout`;
- без скачка часов запуск не останавливается раньше срока;
- во время сна уборка не обещается: машина заморожена, алгоритм остановки
  отрабатывает после пробуждения.

### C. Очередь на логическом времени — сделано (2026-09-09)

`scheduler` больше не принимает `Instant`, а работает с логическим временем;
супервизор считает его как `max(монотонное, wall)`. Без этого
`queue_timeout`, `starvation_after` и `waiting_ms` «замирали» на время сна:
монотонные часы в сне не идут, и очередь после пробуждения ждала бы остаток
срока заново. Тесты: `a_suspend_longer_than_the_queue_timeout_expires_the_request`,
`a_wall_clock_jump_still_expires_a_deadline`.

## Исходное предложение

Дальше — спецификация, по которой делались этапы 1 и 2.

## Цель

Агент запускает тесты через wyd, получает результат и может отменить запуск.
Wyd контролирует время жизни запуска, показывает его в существующих интерфейсах
и ограничивает собственные логи. Следующий этап добавляет общую очередь и бюджеты
ресурсов для нескольких агентов одного пользователя на одной машине.

Первый этап — управление обычными локальными процессами на macOS и Linux.
Он не изолирует файловую систему, сеть, установку пакетов и секреты пользователя.
Второй этап тоже не является полноценной средой для исполнения враждебного кода.
Одноразовые файловые среды и кеш зависимостей описаны как дальнейшее продолжение.

## Основа в текущем проекте

- `src/main.rs`: clap CLI и отдельный scanner loop для TUI.
- `src/server.rs`: Unix socket, последовательная обработка запросов, collector.
- `src/mcp.rs`: stdio MCP, инструменты `list_sessions` и `explain`, синхронный dispatch.
- `src/model/session.rs`: сессия означает invocation агента, а не отдельный тест.
- `src/store.rs`: SQLite/WAL, provenance и идентичность процессов.
- `src/actions/process.rs`: существующие действия сигналят только записанные PID,
  проверяют время старта и намеренно не используют killpg.
- `src/web/mod.rs`: сейчас web отказывается работать одновременно с serve.
- `docs/webmcp.md`: WebMCP готовит очистку, человек подтверждает действие.
- `tests/mcp_conformance.rs`: проверяет настоящий stdio-процесс; схема БД продублирована.

При реализации учитывать существующие незакоммиченные изменения в Cargo.toml,
Cargo.lock, main.rs, store.rs и новый trace.rs. Не переписывать их и не включать
посторонние изменения в коммиты этой функциональности. Версия Cargo.toml — 0.9.0;
раздел Status в AGENTS.md отстаёт, поэтому номера будущих релизов здесь не назначены.

## Продуктовые решения

1. CLI, MCP, TUI и WebMCP используют одну модель запусков и один supervisor.
2. `Run` отделён от `RuntimeSession`; связь с агентной сессией необязательна.
3. Никаких отдельных реализаций исполнения для каждого языка.
4. Пользователь разрешает execution при подключении MCP; после этого разрешённые
   запуски выполняются без дополнительного подтверждения внутри wyd.
5. Текущий режим `wyd mcp` остаётся read-only. Предлагаемый `--allow-run`
   включает инструменты запуска и отмены для данного подключения.
6. В вебе первый этап добавляет наблюдение и подтверждаемую отмену, а не endpoint
   произвольного выполнения команд. Существующая модель WebMCP сохраняется.
7. Wyd не управляет тестами, которые агент запускает мимо него. Интеграция должна
   объяснять агенту использование MCP или `wyd run`; это не системный перехват shell.
8. Бюджеты относятся к запускам wyd одного пользователя, а не ко всем приложениям ОС.

## Этап 1. Управляемые запуски

### 1.1. Контракт Run и хранилище

Добавить `src/model/run.rs` с типами RunId, RunSpec, RunState, RunResult,
CleanupReport и BackendCapabilities.

RunSpec:

- уникальный `request_id` для идемпотентного создания;
- executable и массив аргументов, без неявного shell;
- абсолютный cwd; отдельно определённый project root;
- необязательная агентная сессия, с отметкой происхождения этой связи;
- execution timeout и период мягкого завершения;
- параметры логирования и временного каталога;
- в будущем — требования к ресурсам и backend.

Состояния: `queued → starting → running → stopping → finished`.
До запуска также возможны переходы в finished из-за отмены или ошибки.
В первом этапе queued обычно кратковременно; будущую очередь не надо имитировать.

Причины завершения: `exited`, `signaled`, `timed_out`, `cancelled`,
`spawn_failed`, `supervisor_lost`, `resource_limit` (для этапа 2).
Exit code и сигнал хранятся отдельно. Cleanup: `pending`, `complete`,
`incomplete`, `unknown`; успешный код теста не означает успешную уборку.

Добавить таблицы runs, run_processes, run_events, run_requests или эквивалентную
минимальную схему. Хранить версию записи для событий/курсорного чтения,
backend, supervisor identity, boot identity и временные метки переходов.
Содержимое stdout/stderr — в отдельных ограниченных файлах, не в строках БД.

Одинаковые request_id и спецификация возвращают существующий run; другая
спецификация с тем же ключом даёт конфликт. Дедупликация выполняется транзакционно.
Задать ограниченное окно хранения ключей и документировать его.
Полное окружение, токены доступа и произвольные значения env в БД не записывать.
Команда и её вывод могут содержать секреты: локальные файлы доступны только владельцу;
не обещать автоматическое распознавание всех секретов.

### 1.2. Один локальный supervisor

Добавить `src/runner/` и общий клиент локального API.
Расширить serve до supervisor, принимающего быстрые запросы и события через каналы.
Ни запуск теста, ни ожидание его окончания не блокируют accept/dispatch.
Использовать std threads/channels; не расширять tokio за пределы существующих
Docker scanner/actions без отдельного обоснования.

Первое обращение run может запускать supervisor по требованию. Выбор экземпляра
должен быть атомарным: lock, проверка живого socket и handshake готовности.
Проверки «файл есть» или «соединение удалось» недостаточно для конкурентного старта.
Ограничить размер запросов, число клиентов и время чтения, чтобы зависший клиент
не занимал обработчик бесконечно. Каталог приватный, socket 0600, проверка peer UID
там, где доступна. Локальный API не становится TCP shell-сервисом.

CLI передаёт своё окружение supervisor в памяти для конкретного запуска;
нельзя использовать устаревшее окружение давно запущенного daemon. MCP передаёт
окружение своего подключения с явно заданными overrides. Проверять размеры.
stdin по умолчанию закрыт: первая версия рассчитана на неинтерактивные тесты.
PTY, запросы пароля и интерактивный shell — вне первого выпуска.

Свести collectors активных клиентов к одному переиспользуемому System в одном
scanner thread. Web и MCP читают общий snapshot/API, TUI при наличии supervisor
подключается к нему. Сохранить самостоятельный TUI без обязательного daemon;
предусмотреть передачу владения сканированием при появлении supervisor.
Таймауты runner работают независимо от скорости и ошибок scanner.

Supervisor остаётся жив при активных запусках; запуск по требованию может завершаться
после периода бездействия. Явный `wyd serve` остаётся foreground-сервисом.
Ни автозагрузку ОС, ни login service по умолчанию не устанавливать.

### 1.3. Исполнение и остановка

Сначала сделать небольшой platform spike: запуск отдельной процессной группы,
мягкая/принудительная остановка, безопасное удержание идентичности группы,
обработка выхода лидера и поведения отделившихся потомков. После этого фиксировать
реальный контракт backend в тестах. Не переносить killpg в существующий generic kill.

Для запуска wyd группа создаётся до исполнения пользовательской команды.
Автоматическая остановка не должна опираться на эвристические ownership scores.
Известные процессы идентифицируются boot + PID + start time; при недостаточных
данных runner не должен наследовать fallback «PID достаточно» из старых действий.
Проверки identity уменьшают риск PID reuse, но не устраняют все гонки; применять
OS handles, где доступны, а не обещать атомарность проверки и kill по PID.

После выхода основной команды остановить оставшиеся процессы управляемой группы.
Таймаут, явная отмена и Ctrl-C используют один алгоритм:

1. Атомарно отметить stopping и причину.
2. Запросить мягкое завершение управляемого запуска.
3. После grace period принудительно завершить оставшиеся процессы.
4. Reap доступных детей и проверить доступные свидетельства остаточных процессов.
5. Зафиксировать результат и cleanup report, закрыть ограниченные каналы вывода.

Deadline измеряется монотонными часами. Wall-clock нужен только для истории.
Разрыв MCP/CLI-соединения не отменяет запуск; он продолжает жить до своего deadline.
Явный Ctrl-C CLI отправляет cancel. Повтор cancel безопасен и возвращает актуальный статус.
Поведение при sleep/resume проверить на обеих ОС: по пробуждении просроченный запуск
останавливается; не обещать выполнение уборки во время сна машины.

`setsid`, double fork и запуск через внешние daemon могут вывести работу за пределы
обычной группы. Для таких случаев stage 1 возвращает честную ограниченную гарантию.
Даже `cleanup=complete` означает полноту в рамках backend, а не отсутствие любой
работы, косвенно инициированной тестом. Подтверждённые остатки видны в wyd.

### 1.4. Сбои и восстановление

Перед spawn записать starting и ownership supervisor. Предусмотреть handshake
внутреннего launcher, чтобы команда не начала работу до регистрации запуска.
При сбое в промежутке между spawn и commit не повторять пользовательскую команду
автоматически: вернуть неопределённый результат и сверить launcher identity.
Идемпотентный API не является обещанием exactly-once для внешних побочных эффектов.

При старте supervisor сверяет unfinished runs с boot и процессами.
После reboot старые процессы не сигналятся. При потерянном supervisor не придумывать
exit code: supervisor_lost + cleanup unknown/incomplete. Уборка возможна только
для подтверждённо принадлежащих run процессов; при недостатке данных — диагностика.
SIGKILL supervisor и power loss не позволяют обещать немедленную уборку в stage 1.
Штатный shutdown сначала завершает активные запуски, затем закрывает БД и socket.

### 1.5. Вывод, временные файлы и хранение

Отдельно читать stdout/stderr, не допуская deadlock от заполненных pipe.
Хранить ограниченный хвост вывода со стабильными курсорами и отметкой truncation.
После достижения лимита продолжать дренировать pipe, даже если данные не сохраняются.
Отделить управляющий JSON MCP stdout от вывода дочерней команды.
Невалидный UTF-8 и управляющие последовательности безопасно представлять в UI;
вывод теста не трактовать как инструкции для самого wyd.

Пример стартовых defaults для проверки на прототипе: timeout 10 минут,
grace 3 секунды, 10 MiB логов на run, 250 MiB суммарно, retention 7 дней.
Это предложения, не результаты измерений. Глобальная квота учитывает активные логи;
при нехватке места новые байты отбрасываются с явной отметкой, процесс не виснет.

Создавать run-specific TMPDIR в управляемом каталоге. Это удобство, не sandbox:
программа может писать в другое место. Очистка касается только принадлежащего
wyd каталога, проверяет корень и не следует symlink наружу. Project, node_modules,
venv и системные caches автоматически не удаляются.
Метаданные и журнал событий тоже имеют retention; рост SQLite/WAL контролируется
без дорогого VACUUM на каждом завершении.

### 1.6. CLI и MCP

Предлагаемые CLI:

```text
wyd run --timeout 120s -- npm test
wyd run --cwd /absolute/project --timeout 120s -- python -m pytest
wyd runs --json
wyd logs <run-id> --follow
wyd cancel <run-id>
wyd mcp --allow-run
```

`wyd run` ожидает результат и показывает вывод. Shell-синтаксис — только явно:
`wyd run -- sh -c 'command1 && command2'`. Флаг --json возвращает структурированный
результат, не смешивая его с логами. Обычный exit code команды сохраняется;
для timeout/cancel/spawn failure документировать wrapper-коды (предложение:
124/130/125), а точную причину всегда отдавать в JSON.

MCP tools:

| Tool | Вход | Результат |
| --- | --- | --- |
| start_run | request_id, argv, cwd, timeout_ms, optional session | run_id, state, capabilities |
| get_run | run_id, optional after_revision, bounded wait_ms | state, result, cleanup, revision |
| read_run_output | run_id, cursor, max_bytes | chunks, next_cursor, truncated, eof |
| list_runs | project/session/state, cursor, limit | runs, next_cursor |
| cancel_run | run_id | idempotent current status |

Read tools доступны обычному MCP, start/cancel — execution-enabled подключению.
Проверить актуальный MCP контракт при реализации; не менять protocol version
заодно с runner. Длинное ожидание не блокирует другие запросы или отмену.
session_id — метаданные происхождения, не доказательство авторизации.
Подключение получает область управления созданными им запусками; read-only клиент
не может отменить run через прямой альтернативный API. CLI владельца ОС может
управлять всеми своими runs. Это разделение возможностей внутри wyd, не защита
от произвольного враждебного процесса с тем же UID.

Запуск через MCP не должен неожиданно обходить границы окружения клиента:
описание инструмента явно сообщает host execution. Если клиент работает в sandbox
или удалённо, подключать только сознательно выбранный локальный execution backend;
не обещать автоматическое наследование sandbox-политики клиента.

### 1.7. TUI, web, WebMCP и документация

## Этап 2. Очередь и бюджеты ресурсов

Статус: **реализован** (2026-09-09) в объёме ниже; §2.1–2.5 остаются
спецификацией, фактические отклонения отмечены. Не реализовано: macOS hard
limits (by design), реальный sleep/resume-тест, прогон под настоящим
systemd user-менеджером.

Реализовано:

- `src/runner/scheduler.rs` — детерминированный state machine без OS-кода:
  FIFO внутри проекта, round-robin между проектами, starvation bypass после
  `starvation_after_secs`, атомарные слоты и резервации, лимит очереди,
  немедленный отказ impossible-заявки, отдельный queue deadline.
- `EffectiveLimits` и трёхзначный `Capability` (`Available`/`Monitored`/
  `Unavailable`) в `RunView.requested`/`effective`; hard-запрос проверяется
  `check_capabilities` до spawn.
- macOS: `monitored`-остановка при превышении порога (`resource_limit`,
  exit 137, `limit_event` с числом); измерение — сумма RSS по process group
  каждые 200 ms.
- `get_capacity`/`set_limits` в локальном API и `Client::capacity()/set_limits()`;
  `start_run` принимает `memory_mb`/`enforcement`/`queue_timeout_ms`/
  `cpu_millicores`/`processes`.
- `[runs]` в config.toml и `wyd capacity [--json] [--set key=value]`.
- MCP `get_capacity`; WebMCP `get_capacity` и `GET /api/capacity`; очередь,
  резервации и наблюдаемое потребление показаны в TUI и web раздельно.
- **Linux cgroup v2** — делегированный subtree (`WYD_CGROUP_ROOT` или
  writable ancestor собственной cgroup): `memory.max`, `memory.swap.max`,
  `cpu.max`, `pids.max`, `cgroup.kill`, чтение `memory.events`/
  `cgroup.events`. Ребёнок входит в cgroup между fork и exec, поэтому
  `setsid`-потомок остаётся внутри и убивается вместе с запуском.
  Без делегирования capability = `Unavailable`, hard-запрос отклоняется.
- **Агрегатный родительский cgroup** (`wyd.slice`): `memory.max` = бюджет
  запусков, `memory.swap.max=0`, плюс `cpu.max`/`pids.max` из
  `cpu_budget_millicores`/`pids_budget`, поэтому это kernel-лимиты на сумму,
  а не только политика допуска; `capacity --set …` обновляет их на ходу.
  `get_capacity.aggregate_*` показывает значения. Проверено: потомок без
  собственного лимита упирается в родительский кап (OOM), CPU-квота реально
  тормозит (`cpu.stat`), форк сверх `pids.max` отклоняется (`pids.events`).
- **Делегирование от настоящего systemd** проверено скриптом
  `scripts/systemd-delegation-e2e.sh` в контейнере с systemd PID 1: и
  системный менеджер (`systemd-run --property=Delegate=yes`), и user-менеджер
  с linger — capability `available`, агрегатный кап виден, hard-лимит
  приводит к OOM (exit 137). Никакой ручной подготовки cgroup.
- **`cpu_millicores`/`processes`** — на Linux жёсткие (`cpu.max`,
  `pids.max`); на macOS только запрос и отображение.

Не реализовано и не должно подаваться как реализованное:

- **macOS hard limits** — недоступны by design; `aggregate_memory_limit` =
  `Monitored`, hard-запрос отклоняется до spawn.
- **Реальный systemd user-менеджер** — делегирование в тестах
  подготовлено вручную, автоматического создания unit'а нет и не будет.

### 2.1. Цель и область действия

Несколько агентов разделяют управляемый бюджет, ожидание видно в wyd.
Новые тесты ждут ресурсы, а не стартуют все одновременно.
Ни очередь, ни лимиты runs не гарантируют отзывчивость всей машины: память также
используют IDE, браузер, модели и другие неуправляемые процессы.

### 2.2. Scheduler

Добавить `src/runner/scheduler.rs` — детерминированный state machine без OS кода.
Supervisor единолично выдаёт слоты и резервации; клиенты не решают admission сами.

Параметры: max_parallel, max_parallel_per_project, max_queued,
queue_timeout, общий memory reservation budget и per-run reservation.
Начать с FIFO внутри проекта и round-robin между проектами; ограничить обход
ожидающего большого run, чтобы короткие задачи не вытесняли его бесконечно.
Заявка больше полного бюджета отклоняется сразу, не висит в очереди.
Очередь ограничена; переполнение возвращает конкретную ошибку.

Слоты и память резервируются атомарно до spawn. Время ожидания и execution timeout
раздельны; execution timeout начинается после запуска. В stopping ресурсы ещё заняты.
При incomplete cleanup освобождать резервацию только после сверки либо учитывать
остаток как занятую ёмкость. Иначе следующий запуск обойдёт смысл бюджета.
После сбоя сначала восстановление ресурсов, затем возобновление очереди.
Заявки с истёкшим queue deadline не запускать при рестарте.

Изменение лимитов не убивает текущие runs молча: по умолчанию влияет на admission
и новые runs, интерфейс показывает временное превышение новой настройки.

### 2.3. Backend capabilities и Linux

Добавить capability API: queue, process_group_cleanup, aggregate_memory_limit,
cpu_quota, process_limit, filesystem_isolation; значение available/unavailable
с объяснением и фактически применёнными параметрами для каждого run.

Linux backend использует делегированный cgroup v2 subtree. До запуска проверить
контроллеры, права и поддержку нужных интерфейсов; не требовать запуска всего wyd
как root и не менять глобальную конфигурацию ОС автоматически.
Первый spike выбирает поддерживаемый путь делегирования, например systemd user
service с delegation; прямой delegated path возможен как явная конфигурация.

Родительский cgroup ограничивает все runs, дочерние — отдельные запуски.
Настраивать memory.max, при необходимости memory.swap.max, cpu.max, pids.max.
Supervisor должен оставаться вне ограничиваемого workload subtree, чтобы иметь
ресурсы для обработки OOM и уборки. Launcher помещается в группу до exec/fork
пользовательского кода. Читать memory.events и cgroup.events; не считать каждый
SIGKILL доказательством OOM. Проверять применение параметров и опустошение группы.

Delegation и доступ workload к cgroup требуют отдельной проверки: лимиты обычных
тестов не являются защитой от враждебного кода с теми же правами на cgroup.
Без доступной delegation возвращать unsupported capability, а не запускать команду
с обещанным, но отсутствующим hard limit.

### 2.4. macOS

На первом подэтапе предоставить очередь, reservations, наблюдаемое потребление и
остановку при превышении настроенного порога. Называть режим monitored, а не hard.
Измеряемая память дерева процессов может пропустить краткий пик; сумма RSS может
учитывать shared pages несколько раз. Вид метрики показывать явно.

Для hard aggregate RAM/CPU оставить capability unavailable, пока отдельный
прототип не подтвердит подходящий backend. Если требование hard=true, запуск
отклоняется до spawn. Не подменять его rlimit отдельного процесса или polling.
VM backend для строгого режима — следующий самостоятельный проектный шаг.

### 2.5. API и интерфейсы

Расширить RunSpec требованиями memory, cpu, processes, enforcement и queue timeout.
Ответ get_run содержит requested/effective limits, backend, queue reason,
позицию/ожидание без выдуманного точного ETA, источник метрик и limit events.
Добавить read-only get_capacity в MCP и WebMCP.
Агент может запрашивать меньшие ресурсы, но не увеличивать установленный владельцем
глобальный бюджет или переключать hard → monitored без явного изменения запроса.

UI показывает очередь, занятые слоты, reservations и фактическое потребление
отдельно. Избыточное резервирование не выдаётся за реально занятую RAM.
По OOM/пороговому завершению результат объясняет причину; автоматически не повторять
тест с большими лимитами, поскольку команда могла иметь побочные эффекты.

### 2.6. Последовательность PR и приёмка

1. Scheduler + reservations + ограниченная очередь на обеих ОС.
2. Capabilities и effective limits во всех API/UI.
3. Linux delegation spike, затем cgroup implementation и интеграционные тесты.
4. macOS monitored mode с измерениями overhead и честными метриками.
5. Recovery/pressure scenarios + документация и сквозной demo нескольких агентов.

Проверки: N параллельных заявок не превышают число слотов; одинаковые request_id
не резервируют ресурсы дважды; проекты не голодают; impossible request отвергается;
queue cancel не создаёт процесс; таймаут очереди не расходует execution timeout.
Linux: parent/child budgets, memory OOM, CPU quota, pids cap, detached child внутри
cgroup, отсутствие delegation, очистка после сбоя. Нагрузку держать маленькой и
ограниченной, не использовать неограниченные fork/OOM сценарии на ноутбуке.

Измерения до/после: накладные расходы supervisor в idle, spawn latency без времени
теста, реакция cancel, CPU сканирования, рост диска после 100 запусков,
потребление при нескольких fixtures. Сравнивать одинаковую нагрузку на одной машине;
не публиковать обещания скорости до измерений.

### 2.7. Измерения (2026-09-09, macOS, M-series, debug-сборка)

Один прогон на одной машине, `HOME` в `/tmp`, `max_parallel=4`,
`max_parallel_per_project=2`, бюджет 2048 MiB, default reservation 256 MiB.
Это **не** обещание скорости: debug-сборка и одна конфигурация.

| Метрика | Значение |
| --- | --- |
| spawn latency, тривиальная команда через CLI round trip (10 запусков) | медиана 110 ms, максимум 190 ms |
| idle supervisor | 22–25 MB RSS, 0.2% CPU (collector каждые 2 s) |
| cancel → finished, замер на сокете (без старта CLI) | 77 ms, `outcome=cancelled`, `cleanup=complete` |
| 3 параллельных fixture (`sleep 3`) | supervisor RSS 26 MB; `running=2 queued=1 reserved=512 MiB` (per-project cap: все три в одном cwd) |
| 100 завершённых runs | +2.6 MiB на диске, `state.db` 152 KiB, каталог логов ~0 (команды без вывода) |

Linux-измерений нет (debug/release-сборка в контейнере, не эталонная машина).
macOS hard limits недоступны by design и отклоняются до spawn.

## Дальнейший этап: одноразовые среды

После этапа 2 отдельно спроектировать filesystem/network isolation и dependencies.
Сюда же приходят задачи A и B из «Что делать дальше»: macOS hard-лимиты
появляются как свойство backend'а, а реальный suspend/resume проверяется на
той же VM. Порядок: сначала общий backend (дешёвый уровень задачи A), затем
одноразовая среда, затем прогон сна.

- Linux container backend и Linux VM backend для macOS на готовых механизмах.
- Копия текущего checkout с незакоммиченными и выбранными untracked файлами.
- Одноразовый writable layer; явный экспорт отчётов вместо записи в исходный проект.
- Подготовленные toolchains; dependency cache по lockfile/toolchain/OS/architecture.
- Квоты образов и кеша, eviction, проверка фактически освобождённого места VM-диска.
- Разделение установки зависимостей с сетью и теста с выбранной network policy.
- Проектные сервисы, порты, секреты и интеграционные тесты как отдельные контракты.

Не включать в этапы 1–2 автоматические apt/brew установки, универсальный resolver
окружений, собственный гипервизор, Windows backend или гарантии sandbox security.
Первый критерий перехода: пользователи используют managed runs, но регулярно
сталкиваются именно с загрязнением файлов/зависимостей, которое эти этапы не решают.
